Your agent's audit log is a text file.

It sits on a disk a dozen people can write to, and it is held by the one party with a motive to change it. Proofwire makes every AI agent action policy-gated before it runs and cryptographically provable afterwards — checkable by someone who has every reason to distrust you.

    What “verified” means

    The bundle has not been altered since it was signed, every entry is in the tree, and nothing has been left out of a bundle that says it is complete.

    It does not mean the keys belong to who you think, or that the log records everything the agent did — only what passed through the proxy.

    Two verifiers that don't trust each other

    This page runs a second implementation that shares no code with the CLI. The tests run both over honest, tampered and randomly mutated bundles and require the same answer every time.

    It found two holes in the first: a bundle with its tail cut off verified clean, and witnesses were counted against keys the bundle supplied itself. Both are fixed — try the last two buttons above.

    Three defaults, chosen for the failure mode

    A typo is a load error, not a skipped rule. A misspelled operator inside a deny rule must never quietly read as allow.

    Escalation with no approver resolves to deny. A system that degrades into “allow everything” under stress fails open exactly when it mattered.

    Budgets commit at decision time. Spend recorded on completion means three pipelined refunds all evaluate against an empty ledger, and every one passes a cap they collectively blow through.

  "rules": [

      "then": "deny" },

    Every action leaves a receipt.

    Four properties, each because a specific dispute is foreseeable.

    signed

    Ed25519, deterministic. No per-signature nonce means no way to leak the key by reusing one — which matters when the signer is an unattended runtime producing thousands of signatures an hour.

    chained

    Each receipt commits to its predecessor. Remove or reorder one entry and everything after it breaks. Sequence gaps are visible without any cryptography at all.

    tree-anchored

    RFC 6962 Merkle log — the construction Certificate Transparency uses, checked against its published reference vectors. Inclusion proofs tie a receipt to a root; consistency proofs prove the log only ever grew.

    sealed

    Arguments are salted commitments, not payloads. The log holds sha256(salt ‖ payload) and a preview with secrets masked — so a receipt is publishable as written.

    The third row is the one that matters. A hash chain alone cannot catch it — the rewrite is internally consistent. What convicts it is a checkpoint published before the rewrite, which the new history can no longer reproduce.

    Two problems nobody else solves.

    The split view

    A log that signs its own root can keep two histories and show each auditor a different one. Both verify perfectly in isolation. This is the one attack a self-hosted transparency log cannot defend against alone.

    Independent witnesses close it. A witness counter-signs a root only if it extends the last root it saw, and refuses to sign two roots at the same size. Pin the witnesses you chose, and a split view needs every one of them to collude.

    Erasure vs. audit

    A deletion request and an immutable audit trail are, on the face of it, two duties in direct conflict. Salted commitments dissolve it.

    Destroy the salts, keep the proof. Those payloads become permanently unopenable — by you, by a court, by whoever steals the directory in 2029 — while every signature, chain link and inclusion proof still verifies.

    For teams: a hub you don't have to trust.

    One log your whole organisation writes to, with shared policy, an approvals inbox and witnesses — without the hub ever being able to forge a receipt, or to stop you working when it's down.

    The hub never holds a signing key

    Agents sign locally. The hub verifies every receipt on arrival and stores only what it can verify. That leaves it able to do exactly three dishonest things, each with a defence: altering a receipt breaks the signature, dropping one breaks the chain, and showing two customers two histories is what witnesses exist to refuse.

    And it isn't load-bearing

    An agent whose hub is unreachable keeps running, keeps recording locally, and ships the backlog when it returns. An audit service that could halt production would be removed from production after its first outage.

    shared policy

    Versioned and immutable. Agents fetch the active one at startup and record its hash in every receipt, so a decision can always be traced to the exact rules in force.

    approvals inbox

    Escalations reach a human. Undecided requests expire into a denial — never into an approval. Reviewers see redacted arguments.

    tenant isolation

    Every row names its organisation. A credential cannot reach another tenant's data by any route, including by guessing an id — and agent keys are pinned to a single log.

    keys out of the database

    A KMS or HSM can hold them. Signing goes through a three-member interface, so a misconfigured signer disables signing rather than quietly falling back to a local key.

      What it doesn't do.

      A security tool that overstates its guarantees is worse than none, because it buys confidence it hasn't earned.

      • The cryptography has not been reviewed by anyone independent. It is checked against published RFC 6962 and RFC 8032 vectors rather than only against itself, and against a second implementation that shares none of its code — which is not the same thing. A review brief is written and waiting.
      • It cannot prove an action it never saw. An agent with a second, unwrapped path to the same API leaves no receipt. This is the most likely real-world failure, and it is a deployment problem, not a cryptographic one.
      • It cannot stop someone with the signing key writing false receipts going forward. It can stop them rewriting the past, once a checkpoint has been witnessed. Keep the key in a KMS.
      • Witnesses are only as independent as you make them. Three witnesses on infrastructure you control are one witness.
      • A restored hub cannot detect its own staleness. The evidence was in the data the restore discarded; only an agent or an auditor holding later evidence can see the gap.
      • There is no hosted service. You run everything yourself — the Dockerfile is built, driven end to end and smoke-tested in CI on every push, but nobody operates it for you yet.
